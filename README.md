# recordlink — 跨源采集记录实体消歧、属性冲突仲裁、可解释归并、主数据合并回滚。

运行栈：Python 3.11+ 标准库 `sqlite3` + `pytest`（离线，无需联网）

## 运行方式
读 `fixtures/input.json` → `loader` → `normalizer` → `keyer` → 幂等落 `sqlite`
→ `blocking` → `scoring` → `match` → `arbitration` → `merge` → `explain` → 代次发布。
```text
make run     # 运行离线流程，输出摄取数量、落库行数、实体数、代次等
make test    # 运行项目测试，包括流水线和幂等性检查
```
CLI 子命令：
```text
python -m recordlink.cli                 # 运行流水线
python -m recordlink.cli explain ENT_ID  # 查看主实体完整解释（决定/谱系/引用/操作史）
python -m recordlink.cli review          # 查看待审项
python -m recordlink.cli undo OP_ID      # 撤销一个合并操作
```

## 数据流与模块边界
每个业务阶段保持单一职责；`pipeline.py` 只负责按顺序调用阶段，不在编排层加入业务判断。
业务模块：`blocking`, `scoring`, `match`, `arbitration`, `merge`, `explain`, `rollback`。
通用模块：`loader / normalizer / keyer / store / pipeline / cli / config / models`。

## 关键语义

### 主键（keyer）
主键是源限定的 `src:id`：同一来源内相同 id 幂等去重；不同来源的相同 id 是
不同记录，绝不互相覆盖。无 id 记录按规范化内容派生稳定散列键。

### 候选生成（blocking）
按配置规则分桶，只在同桶内展开成对比较。报告明确说明覆盖范围与计算成本：
- 超大桶（> `max_bucket_size`）跳过展开，报告记录跳过的比较数与漏合并风险；
- 缺字段记录按规则点名，未产生任何候选的记录列入 `uncovered`；
- `estimated_comparisons` 为实际展开的成对比较数。

### 评分（scoring）
区分“未知”与“强冲突”：任一侧缺失/空值/被删除 => 该字段未知，不参与加权；
全部字段未知时总分为 `None`（未知，不是 0）。冲突字段（如地址）双方有值且
相似度低于冲突阈值 => 强冲突，无论总分多高都阻断自动合并。

### 匹配（match）
阈值分三档：自动合并 / 待审 / 不合并；未知证据进待审而非当作不相似。
聚类不是“超过阈值就连通”：合并两个分量前检查全部跨分量已知证据，存在强冲突
或已知不相似则阻断并保留待审——A-B、B-C 相似但 A-C 冲突时不会连成一个实体，
一对多歧义同样保留待审。

### 裁决（arbitration）
主值 = 来源可信度 × 新鲜度（指数衰减）加权，人工覆盖（实体级/记录级）优先，
字段类型策略：`scalar`（权重最大）/ `latest`（最新）/ `set`（并集）。
严格区分四种“无值”：`missing`（缺失，不投票）、`empty`（空值投票）、
`deleted`（源删除标记 `{"$deleted": true}`，删除投票）、`retracted`
（整条记录被来源撤回，全部投票撤回）。前两名候选权重接近 => 证据不足，
属性保留待审（`pending_review`），不进主值。

### 合并（merge）
合并操作有确定性 op_id：重复提交是幂等空操作；实体带单调版本号，
应用时校验期望版本，不一致报 `VersionConflict`（并发冲突）。
合并保留：裁决后的属性、属性级来源谱系（`lineage`）、引用迁移记录
（`ref_migrations`，外部记录对成员键的引用迁移到主实体）。

### 解释（explain）
解释对应实际发生的决定与历史证据：合并解释记录真实决策边（分数、理由、
阈值、规则版本），裁决解释记录真实候选、权重与来源。指纹未变的实体不重写
解释；历史代次的解释全部保留，可按代次追溯。

### 增量重算与代次发布（store / pipeline）
每个簇的指纹 = 规则版本 + 成员内容 + 相关人工覆盖 + 裁决配置。规则换版或
迟到证据只让指纹变化的簇重算，其余实体与解释原样沿用。一个代次的全部变更
与代次指针在同一事务提交（完整发布）；崩溃只会留下未提交事务，`recover()`
在连接时清理任何越过当前指针的孤儿行，保证恢复后主实体、引用、裁决、解释一致。

### 撤销（rollback）
撤销按依赖分两种路径，撤销本身幂等：
- 无后续依赖：按 `prev_versions` 快照恢复，主实体退役、被吸收实体复原、
  引用迁移撤回，成员记录补建单记录实体；
- 有后续依赖（后续合并已消费该实体）：补偿式拆分——只剥离该操作贡献的成员，
  剩余成员原地重算，被剥离成员形成拆分实体，引用按来源记录改指；
  后续无关内容（后到成员、人工覆盖、不相关属性）保持不变。

## 记录状态约定
- 记录级：`"deleted": true` 源删除墓碑；`"retracted": true` 来源撤回。
  两者都保留行（幂等、可审计），但不参与候选、评分与裁决。
- 字段级：缺失（字段不存在）、空值（`null`/`""`）、删除（`{"$deleted": true}`）。
- 人工覆盖：`store.set_override(con, scope, target, attr, value)`，
  `scope` 为 `record` 或 `entity`，跨代次生效，移除后按证据重新裁决。

## 权衡说明（误合并 / 漏合并 / 执行成本）
- 误合并防线：强冲突阻断、冲突感知聚类、证据不足待审；
- 漏合并防线：多分桶规则、未知证据进待审而非直接否、超大桶在报告中点名风险；
- 成本防线：分桶限制成对比较数量级，超大桶跳过并记账，指纹门控避免全量重算。
